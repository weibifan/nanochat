# NanoChat 中文数据集完整训练 · 使用说明

用**中文数据集**在 **Windows CPU** 上跑通 NanoChat 完整流水线：
`下载数据 → 训练 tokenizer → 预训练 → 评测 → SFT → 中文对话`。

所有步骤脚本在 `runs-in-ch/` 下，**不改任何原文件**（nanochat/、scripts/、tasks/ 均只读），
中文适配全部通过新增的 `*_ch` 文件实现。

---

## 1. 概述（运行环境 + 产物位置速查）

> 本套件的**默认目标机器是 Windows CPU**（本机实测见 1.1）。若换到**带单 GPU** 的机器，
> 改动见**第 4 节（在 GPU 环境运行）**。

### 1.1 运行环境（本机实测）

| 项目 | 值 |
|---|---|
| CPU | Intel i5-14400（10 核 16 线程） |
| 内存 | 32 GB |
| 系统 | Windows（控制台默认 GBK 编码） |
| Python | 3.10（uv 环境，`.venv\Scripts\python.exe`） |
| PyTorch | 2.9.1+cpu，fp32（无 AVX512，bf16 反而更慢） |
| 编译器 | **无 MSVC**（缺 `cl`，`torch.compile` 无法编译，见 1.2） |
| 磁盘 | `nanochat\data\` 约 8 GB |

### 1.2 Windows CPU 三个关键坑（已由 `_common.py` 自动处理）

1. **`torch.compile` 不可用**：本机没有 MSVC `cl` 编译器，Inductor 无法编译生成的 C++ 代码，
   一调用就报 `Compiler: cl is not found`。`_common.py` 设置 `TORCH_COMPILE_DISABLE=1`，
   让 `torch.compile` 退化为 eager 模式（`base_train`/`chat_sft`/`optim.py` 里的
   `torch.compile` 直接通过）。
2. **线程数必须显式设满**：PyTorch 默认 10 线程（物理核），实测 28 s/step；设满 16 线程后
   9.7 s/step（快 ~3 倍）。Windows 下 `OMP_NUM_THREADS` 环境变量无效，只能
   `torch.set_num_threads(16)`，因此 torch 步骤都用 `run_module_inproc()` 在**进程内**运行。
3. **控制台 GBK 编码**：原版 banner 里的制表符（`░`）在 GBK 下抛 `UnicodeEncodeError`。
   `_common.py` 把 `stdout/stderr` 重配为 UTF-8（子进程靠 `PYTHONIOENCODING` 继承）。

> 默认所有步骤都用 `python runs-in-ch/stepX.py` 从**项目根目录之外**运行也行——
> `_common.py` 会通过 `__file__` 推导 `NANOCHAT_BASE_DIR = <项目根>/data`（绝对路径），
> 并把项目根加入 `sys.path`，与调用时的 cwd 无关。

### 1.3 产物位置速查（都在 `nanochat\data\` 下）

| 内容 | 路径 | 参数量 | 来源 |
|---|---|---|---|
| **分词模型** | `data\tokenizer\tokenizer.pkl`（BPE）+ `data\tokenizer\token_bytes.pt`（token 字节表） | — | step2 |
| **预训练模型** | `data\base_checkpoints\d6\model_000050.pt`（+ `meta_000050.json` 配置、`optim_000050_rank0.pt` 优化器状态） | **7353 万**（wte 12.6M + value_embeds 37.7M + lm_head 12.6M + 矩阵 10.6M + scalars 38） | step4 |
| **SFT 微调模型** | `data\chatsft_checkpoints\d6\model_000049.pt`（+ `meta_000049.json`、`optim_000049_rank0.pt`） | 同上（同一 6 层/384 维模型） | step6 |
| 预训练语料 | `data\base_data_climbmix\shard_*.parquet`（13 片，末片为 val） | step1 |
| 任务数据 | `data\task_data\smoltalk-chinese\`、`gsm8k_zh\`、`ceval\` | step1 |

> step7 会自动加载 `chatsft_checkpoints\d6\` 中 step 编号**最大**的模型。
> 各模型均为 fp32，权重约 294 MB，优化器状态约 546 MB。

### 1.4 完整版 vs 练习版

当前默认是**练习版**（目标：整条流水线快速跑通，本机每步都在分钟级）：

| 步骤 | 练习版 | 完整版（runcpu.sh 同款超参） |
|---|---|---|
| step4 预训练 | 50 迭代（11 min） | 5000 迭代（估 15–16 h） |
| step6 SFT | 50 迭代（~15 min） | 1500 迭代（估 4–5 h） |

改回完整版：把 `step4_base_train.py` / `step6_chat_sft.py` 里的迭代数改回 5000/1500 即可
（或在 step6 用 `NANOCHAT_SFT_ITERS` 环境变量）。

## 2. 各步骤：配置与实测耗时

### step1 — 准备中文数据集

```bat
python runs-in-ch/step1_prepare_data.py        :: 默认隔片取 4 片
python runs-in-ch/step1_prepare_data.py --num-parts 8   :: 取更多片
```

**配置**
- Ultra-FineWeb-zh 4 片（默认隔片取样 001/086/171/256，ModelScope 下载，约 5 GB），
  重打包成 ClimbMix 格式（250M 字符/shard、zstd、片内 seed 洗牌）
  → `data/zh-ch/base_data_climbmix/shard_*.parquet`（13 片，最后 1 片为验证集）。
- SFT 对话数据 `opencsg/smoltalk-chinese` 19 个类目 → `data/zh-ch/task_data/smoltalk-chinese/`。
- 数学/多选题 `testUser/GSM8K_zh`、`opencompass/ceval-exam`（解压 dev/val/test）
  → `data/zh-ch/task_data/gsm8k_zh/`、`data/zh-ch/task_data/ceval/`。

**实测耗时**：下载 4 片 515 s（≈8.6 min）+ 重打包与任务数据下载，整步约 **12 min**。
（幂等：已存在的文件自动跳过，重跑很快。）

### step2 — 训练中文 BPE tokenizer

```bat
python runs-in-ch/step2_tok_train.py
:: 可用环境变量覆盖：
::   NANOCHAT_MAX_CHARS=300000000（默认）
::   NANOCHAT_VOCAB_SIZE=32768（默认）
```

**配置**：300M 字符 + 32768 词表（nanochat 默认词表即 32768）。中文无空格、序列长，
BPE 的 pair-count 随字符数线性增长且与词表无关，词表只影响 merge 阶段：
- 300M/32768 档可跑完（~25 min）；1B/65536 档会 OOM 或跑几小时（本机 32GB 不够）。
- 详见 `step2_tok_train.py` 头部注释里的 rustbpe 实测记录。

**实测耗时**：**24.8 min**（其中 pair-count ~8 min + merge ~13 min）。
产物：`data/zh-ch/tokenizer/tokenizer.pkl`、`token_bytes.pt`。

### step3 — tokenizer 压缩率评测

```bat
python runs-in-ch/step3_tok_eval.py
```

**配置**：原版 `tok_eval` 默认参数，对比 GPT-2/GPT-4 在不同文本上的压缩率。

**实测耗时**：**1.7 min**。结果（中文语料 climbmix-train/val）：
本 tokenizer **4.48/4.39 bytes-per-token**，约为 GPT-2（1.42）的 **3.2 倍**、
GPT-4（2.34）的 **1.9 倍** 好——中文 BPE 有效学到了中文子词。
（英文 news/science 等仍是 GPT 系占优，符合预期。）

### step4 — CPU 预训练（base_train）

```bat
python runs-in-ch/step4_base_train.py        :: 练习版 50 迭代
:: 想跑完整版：把脚本 argv 里的 --num-iterations=50 改回 5000
```

**配置**（与 runcpu.sh 相同，仅迭代数不同）
- 模型：depth=6、head-dim=64、window-pattern=L、max-seq-len=512 → n_layer=6 / n_embd=384 /
  n_head=6 / 词表 32768，**7350 万参数**（wte 12.6M + value_embeds 37.7M + lm_head 12.6M + 矩阵 10.6M）。
- 训练：device-batch=32、total-batch=16384（1 次梯度累计）、5000 迭代正式版。
- 评测：eval-every=100（正式）→ 练习版 25、eval-tokens=524288（正式）→ 练习版 32768、sample-every 同理。
- 数据：`data/zh-ch/base_data_climbmix/`（中文）。

**实测耗时**：练习版 50 迭代整步 **11.2 min**（训练循环 6.4 min；其余为建模型/初始化/2 次 eval/保存）。
单步 ~9.7 s（16 线程、fp32 eager）。**正式版 5000 迭代估算 15–16 h**（含 eval 开销）。

结果（练习版）：loss 10.40 → **9.01**，val bpb 3.38 → **2.91**，明显在学习中文。
产物：`data/zh-ch/base_checkpoints/d6/model_000050.pt`。

### step5 — 预训练模型评测

```bat
python runs-in-ch/step5_base_eval.py
```

**配置**：`--device-batch-size=1 --split-tokens=16384 --max-per-task=16 --eval=bpb,sample`
（跳过 core：CORE 是英文 ICL 基准且需从海外 S3 下载，对中文模型意义不大）。

**实测耗时**：**0.2 min**。结果：train bpb **2.71**、val bpb **2.87**；
无监督采样已输出成段中文（练 50 步即学到中文分布）。

### step6 — 中文 SFT（chat_sft）

```bat
python runs-in-ch/step6_chat_sft.py        :: 练习版 50 迭代
set NANOCHAT_SFT_ITERS=1500 && python runs-in-ch/step6_chat_sft.py   :: 完整版
```

**配置**：继承预训练模型/超参，SFT 混料 =
SmolTalkCh(train) + MMLUCh×3（C-Eval dev+val）+ GSM8KCh×4（GSM8K_zh），共 **518,444 条**。
`--chatcore-every=-1` 跳过 ChatCORE（英文基准，且 C-Eval/GSM8K_zh 格式会打爆其 JSON 解析）。
练习版 50 迭代；完整版 1500 迭代。

**中文数据两个关键适配（都在 `tasks/*_ch.py`，不改原文件）：**
- **smoltalk-chinese 对话偏长**：实测 **51.8% 超过 513 token**（中位数 552），而 SFT 窗口只有 512。
  bestfit 打包器塞不进去的对话会整行变 padding，整 batch 无监督 token 时
  `cross_entropy(ignore_index=-1)` 会 **0/0 = NaN**，模型直接报废。
  解决办法：`filter_conversations()` 只保留渲染后 ≤512 token 且 ≥1 个 assistant 监督 token 的对话
  （483,734 → 226,161 条），结果缓存到 `data/zh-ch/task_data/smoltalk-chinese/_valid_indices.pkl`。
  **换 tokenizer 后记得删除该缓存。**
- **C-Eval 只有 ~1606 题**，但 chat_sft 的 val 用 `MMLU(..., stop=5200)`，
  `Task.__len__` 会按 5200 造 index_map，越界。`MMLUCh.__init__` 把 stop 夹紧到实际题数。

**实测耗时**：练习版整步 **22.2 min**（训练循环 17.2 min；本次运行期间有后台负载，
单步 ~26 s；空闲时单独实测单步 ~11 s，50 迭代约 10–12 min）。
**完整版 1500 迭代估算 4–5 h**。

结果（练习版）：val bpb **2.48 → 1.97**，无 NaN，loss 正常收敛。
产物：`data/chatsft_checkpoints/d6/model_000049.pt`。

### step7 — 中文对话

```bat
python runs-in-ch/step7_chat_cli.py "中国的首都是哪个城市？"   :: 单次问答
python runs-in-ch/step7_chat_cli.py                          :: 交互式（输入 quit 退出）
```

自动加载 `data/chatsft_checkpoints/d6/` 里 step 最大的模型。

**实测耗时**：**0.1 min**（加载模型 + 生成）。练习版模型已能用中文回复
（内容仍是"语无伦次"的幻觉，这是 50 步练习模型的正常水平；正式版 1500 步会好得多）。

## 4. 在 GPU 环境运行：代码改动建议（单 GPU）

> 本套件的默认目标机器是 **Windows CPU（无 GPU、无 MSVC）**。若换到**带单 GPU** 的机器，
> 只需少量改动。整体结论：**设备切换本身几乎零代码改动**——原版 `nanochat/common.py`
> 的 `autodetect_device_type()` 已按 `CUDA → MPS → CPU` 自动选设备，dataloader 也内置了
> `pin_memory` + 非阻塞拷贝。真正要动手的只有 `_common.py` 的 `torch.compile` 开关，
> 以及 step4/step6 的训练参数。

### 4.0 共同前提（两种平台都一样）

1. **把 PyTorch 换成 CUDA 版**（当前是 `2.9.1+cpu`），装好后确认
   `python -c "import torch; print(torch.cuda.is_available())"` 输出 `True`。
2. **计算精度由硬件自动决定**：`common.py` 按 SM 版本选择 COMPUTE_DTYPE——无需手动指定
   （SM ≥ 8.0 用 bf16，否则回落到 fp32；Pascal/Maxwell 时代不要开 `--fp8`（需 H100+））。
3. **设备选择不用改代码**：step4/step6 的 argv 没传 `--device-type`，空值 = 自动检测；
   想更明确可自行补 `--device-type=cuda`。
4. **CPU 活不受 GPU 影响**：step1（下载/重打包）、step2（rustbpe 训 BPE）、step3（tok_eval）、
   step5（BPB/采样评测）仍是 CPU 逻辑，GPU 上同样执行、不加速。
5. **检查点/数据路径不变**：CPU 与 GPU 的检查点格式一致，可互相加载。

### 4.1 变更清单总表

| 改动点 | Windows + 单卡 | Linux + 单卡 |
|---|---|---|
| `_common.py` 的 `TORCH_COMPILE_DISABLE=1` | 按 MSVC 有没有决定（见下） | **建议放开**（收益最大） |
| `--device-type` | 可不加（自动检测） | 可不加（自动检测） |
| `--device-batch-size` 等 | 按显存调大 | 按显存调大 |
| 线程/UTF-8 相关 hack | 保留无害 | 可简化（见下） |
| 完整版迭代数 | 可开 5000/1500 | 可开 5000/1500 |

### 4.2 Windows + 单 GPU（例如 GTX 1080 8 GB）

| 项目 | 建议 |
|---|---|
| **torch.compile** | 若无 MSVC `cl`：保持 `_common.py` 的 `TORCH_COMPILE_DISABLE=1` 不动。若机器已装 VS C++ 工具链（`cl` 在 PATH），只需确认 `python -c "import triton"` 不报错，然后**放开禁用**，即可获得编译加速 |
| **精度** | 1080 是 Pascal（SM 6.1 < 8.0）→ 自动 fp32；不推荐 fp16（该卡无 Tensor Core，fp16 速率约 1/64） |
| **显存 / batch** | 8 GB 对 d6（7350 万参数，fp32 权重 294 MB + 优化器 546 MB）很富余，`--device-batch-size=32` 可提到 128；注意 `total-batch-size` 需是 `device_batch×seq_len` 的整数倍 |
| **线程 hack** | `run_module_inproc` 的 16 线程对 GPU 无碍，保留即可 |
| **`expandable_segments`** | `base_train.py` 头部的 `PYTORCH_ALLOC_CONF=expandable_segments` 在 Windows 上若不受支持只打 warning 并回落静态段，可忽略 |
| **验证** | 先跑 step4 练习版，看单步 `dt` 从 ~10 s 降到亚秒级即成功 |

### 4.3 Linux + 单 GPU（例如 RTX 4090 24 GB）：与 Windows 的差异及改动

| 项目 | 建议 |
|---|---|
| **torch.compile** | Linux 上 CUDA build **自带 Triton**，不再需要 Windows 的 MSVC `cl`，但 Inductor 编译生成的 C++ wrapper 仍需 **GCC 工具链（`g++`）**：先 `sudo apt install build-essential`（缺 `g++` 会报 `Compiler: g++ is not found`）。装好后**强烈建议放开**：删除/注释 `_common.py:33` 的 `TORCH_COMPILE_DISABLE=1`，让 `torch.compile` 真正编译。这是收益最大的一处改动 |
| **精度** | 4090（SM 8.9 ≥ 8.0）→ 自动 **bf16**（主权重仍 fp32），比 Windows CPU 的 fp32 更快 |
| **线程 / 编码** | Linux 上 `OMP_NUM_THREADS` 环境变量有效、控制台默认 UTF-8，`run_module_inproc` 的"设线程/UTF-8"hack 可简化：改回 `run_module`（子进程，顺带每步结束释放 GPU 显存），非必须 |
| **显存 / batch** | 24 GB 更富余：`--device-batch-size` 可到 64~128，`--eval-tokens` 可恢复正式值 `524288` |
| **模型深度** | 可把 step4 的 `--depth=6` 升到 12（乃至 24）。下游 `find_largest_model()`（checkpoint_manager.py）自动挑深度最大的 d 目录，**d6→d12 无缝衔接**，step6/7 不需改 tag；想保留旧目录用 `--model-tag` 分开 |
| **完整版** | 把 step4 改回 `--num-iterations=5000`、step6 改回 1500：完整流水线从 Windows CPU 的 15–16h / 4–5h 缩到小时级甚至更快 |
| **`expandable_segments`** | Linux/CUDA 原生支持，无需处理 |

### 4.4 小结

- **Windows 单卡**：改环境（换 CUDA torch），按「有无 MSVC」决定要不要开 compile（见 4.1），调大 batch。其余基本不动。
- **Linux 单卡**：改环境（CUDA torch）+ **放开 `torch.compile`** 这两件事收益最大；线程/编码 hack 可顺带简化；模型升深度和跑完整版随心所欲。
- 两者**都不需要**给 `dataset_ch` / `tasks/*_ch` / step 脚本做 GPU 相关的代码改动，GPU 相关逻辑已被 `common.py` 自动检测兼容。

## 5. 常见问题

- **报 `UnicodeEncodeError: 'gbk' codec can't encode ...`**：确认用的是 `runs-in-ch/` 下的
  step 脚本（它们会重配 UTF-8）。
- **报 `Compiler: cl is not found`**：torch.compile 需要 MSVC。`_common.py` 已自动禁用；
  若想真正用上 compile，需安装 VS C++ 工具链并让 `cl` 进 PATH。
- **SFT 出现 loss=NaN**：检查是否删掉了 `_valid_indices.pkl` 缓存却换了 tokenizer，
  或手动改了对话过滤逻辑。
- **step6 很慢**：先确认没有其他进程占 CPU；空闲时单步 ~11 s。
- **tokenizer 想重训**：删 `data/zh-ch/tokenizer/` 再跑 step2（顺带删 `_valid_indices.pkl`）。
