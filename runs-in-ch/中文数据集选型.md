# 中文数据集选型（让 nanochat 学会中文）

> **目的**：nanochat 官方是在**英文数据**上训练的——分词器用英文语料训练 BPE，预训练吃英文文本，SFT/RL 也是英文对话。结果模型只"认识"英文，几乎不会中文。本任务的目标：为 nanochat 的每一类英文数据集**找到量级、类型、质量相当的中文替代**，并给出一个可直接落地的**组合**与**代码修改思路**，让 nanochat 也能训练/微调出会中文的模型。
>
> 英文数据源：`第1章=tokenizer/附件4=预训练语料介绍.md`（ClimbMix-400B）与 `第4章=sft+rl/附件3=微调数据集介绍.md`（smol-smoltalk / MMLU / GSM8K）。候选链接以 **ModelScope** 或 **Gitee** 为主（国内可直连）。

---

## 1. 中文与英文的差异，及 nanochat 为何无法识别中文

### 1.1 中文 vs 英文的本质差异

| 维度 | 英文 | 中文 |
|------|------|------|
| **书写** | 单词由字母组成，词间有空格 | 汉字连排，**词之间没有空格** |
| **分词** | 天然空格分词 | 需要 jieba 等分词器，或让 BPE 自己学"字/词" |
| **编码** | 单字节字母（ASCII） | UTF-8 下每汉字 **3 字节** |
| **BPE 合并** | 字母→音节→词根→词 | 偏旁/字→双字词→四字词，**需要更多 merge 才能成词** |
| **词表需求** | 32K~50K 足够 | 常用字 ~3500，但词要 ~几万，**64K+ 更稳** |
| **语料规模** | 400B token 级 | 开源最大约 150B~1.5T 字符级 |

### 1.2 nanochat 为什么"只认识英文"

nanochat 的 BPE 分词器是**从语料中学习 merge 规则**的（`tok_train.py`），它不内置任何语言知识。链路如下：

```
ClimbMix-400B（英文为主） ──→ 训练 BPE ──→ 词表里几乎没有中文 token
                                        ──→ 中文文本被拆成零散字节/单字，压缩率极低
                                        ──→ 预训练从未见过中文，参数里没有中文知识
                                        ──→ SFT 对话也全是英文，不会用中文回复
```

具体表现：
- **分词爆炸**：中文一句话被拆成很多 token（每字可能 1~2 个 token），有效上下文被浪费
- **乱码式生成**：模型可能把中文当字节流预测，输出毫无意义
- **无法对话**：即使你输入中文，模型也不理解指令，更答不出中文内容

### 1.3 要让 nanochat 学会中文，需要换什么

| 环节 | 现在用的（英文） | 需要换成（中文） |
|------|----------------|----------------|
| Tokenizer | `tok_train.py` 在 ClimbMix 上训练 | 在**同一份中文预训练语料**上重新训练（只取前 ~2B 字符，vocab 建议调大） |
| 预训练 | ClimbMix-400B | **与分词器同一份**中文预训练语料（SkyPile / Ultra-FineWeb 等，用量更大） |
| SFT | smol-smoltalk + MMLU + GSM8K | 中文对话 + 中文多选题 + 中文数学题 |
| RL | GSM8K | 中文数学题（GSM8K_zh 等） |

> 关键：**tokenizer 必须重训**（第 4 节会讲），否则中文效果起不来；换预训练语料时 `dataset.py` 的 URL 也要改。

## 3. 中文数据集选型

### 3.1 推荐组合（一句话结论）

> **核心原则（对应官方设计）**：分词器和预训练用**同一个中文语料**，只是规模不同——分词器取其中 ~2B 字符训练 BPE，预训练消费同一语料（CPU 取 ~8 shard、GPU 取更多）。下面推荐组合都遵循这一点：**选 Ultra-FineWeb-zh 就全程用它，选 SkyPile-150B 也全程用它**，只是分词器用 2B 字符抽样、预训练用更大规模。

| 阶段        | 英文（官方）                                      | 中文（推荐）                           | 理由                                                                               |
| --------- | ------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------- |
| Tokenizer | ClimbMix-400B 的 **7 个 shard**（约 2B 字符）      | **Ultra-FineWeb-zh 抽样 \~2B 字符**  | 与预训练**同一套语料**，只是用量不同（对应官方"一料两用"设计）；中英差异大，必须重训 BPE                                |
| 预训练       | ClimbMix-400B 的 **170 个 shard**（约 42.5G 字符） | **Ultra-FineWeb-zh 抽样**（120B token） | 量级最接近 ClimbMix，且是"过滤后的高质量"语料，与 ClimbMix 的"筛选过"属性对齐；SkyPile-150B 作为备选（选它则分词器也改用它） |
| SFT 对话    | smol-smoltalk (460K)                        | **smoltalk-chinese** (\~70万)     | 类型 1:1 对应，连生成流程都复刻 SmolTalk                                                      |
| SFT/评测 多选 | MMLU                                        | **C-Eval**（+CMMLU 备选）            | 中文多选的公认对标                                                                        |
| SFT/RL 数学 | GSM8K                                       | **GSM8K\_zh**（+MetaMathQA 备选）    | 直译版，`#### 数字` 与工具调用格式保留，RL reward 可直接复用                                          |

### 3.2 runcpu.sh 时如何配置（CPU 演示，小规模）

runcpu.sh 全链路都是"缩小配置"，中文版只需要**替换数据源**，训练超参可保持：

> **Ultra-FineWeb-zh 如何按片抽样**：zh split 位于 `data/zh-ch/ultrafineweb_zh/`，由 **256 个 parquet** 组成（`ultrafineweb-zh-part-000-of-256.parquet` ~ `part-255-of-256`），天然可按"片数"选，**无需下载全部**（单文件 URL 直连，见 §4.2 方案 B）。两点注意：
> 1. **每片按行数切**（131M 行 / 256 ≈ 51万行/片，120B token / 256 ≈ 470M token/片），字符量接近 **700M~1G/片**，所以 tokenizer 的 2B 字符**只需 ~2-3 片**（对应 ClimbMix 的 7-8 片，不是同数量级）。
> 2. **片序可能按来源聚合**（IndustryCorpus2 / MiChao / WuDao / SkyPile…），**不要只取前 N 片**，应隔片抽样（如 000/004/008/…）保证来源多样，或下载后重打包时洗牌。

```bash
# ===== 0) 抽样下载 Ultra-FineWeb-zh（隔片取样，不下载全部 256 片）=====
# 单文件 URL 直接下载（ModelScope）：
#   https://modelscope.cn/datasets/OpenBMB/Ultra-FineWeb/resolve/master/data/ultrafineweb_zh/ultrafineweb-zh-part-000-of-256.parquet
# tokenizer ~2B 字符 ≈ 2-3 片；CPU 预训练复用同一批切片即可

# ===== 1) Tokenizer：与预训练同一语料（下载的 zh 分片）重训，vocab 调大到 64K =====
python -m scripts.tok_train --max-chars=2000000000 --vocab-size=65536

# ===== 2) 预训练：同一批 zh 分片重打包后消费（等价 ClimbMix ~8 shard / ~2B 字符）=====
# 见 §4.2 方案 B：content→text 改名、洗牌、~250M 字符/片重切
python -m scripts.base_train --depth=6 --head-dim=64 \
    --max-seq-len=512 --num-iterations=5000

# ===== 3) SFT：用 smoltalk-chinese 替代 smol-smoltalk =====
python -m scripts.chat_sft --eval-every=200 --num-iterations=1500
```

> 说明：CPU 模式数据量小，`--vocab-size=65536` 比英文的 32768 大一倍，保证中文有足够词表空间。`chat_sft.py` 内部混料（MMLU→C-Eval、GSM8K→GSM8K_zh）通过第 4 节代码修改后自动生效。

### 3.3 speedrun.sh 时如何配置（GPU 全量）

```bash
# ===== 0) 后台抽样下载更多 Ultra-FineWeb-zh 分片（总字符量 ~42.5G，对应 170 shard）=====
# 隔片取 part（如 000/004/008/...），下载总量 ≈ 42.5G 字符
# （Ultra-FineWeb-zh 每片近 700M~1G 字符，约需 50 片；重打包后再切成 ~250M/片）
# 同样不要只取前 N 片，避免来源单一

# ===== 1) Tokenizer：与预训练同一语料的前 2B 字符重训（vocab 65536）=====
python -m scripts.tok_train   # Ultra-FineWeb-zh，只需 2-3 片

# ===== 2) 预训练：同上文中文语料，隔片抽样下载更多分片 =====
# （与 0) 合并：先 -n 小量供 tokenizer，再后台补足预训练量）

# ===== 3) 8 GPU 分布式预训练 =====
torchrun --standalone --nproc_per_node=8 -m scripts.base_train \
    --depth=24 --target-param-data-ratio=8 --device-batch-size=16 --fp8

# ===== 4) SFT：smoltalk-chinese + C-Eval + GSM8K_zh =====
torchrun --standalone --nproc_per_node=8 -m scripts.chat_sft
torchrun --standalone --nproc_per_node=8 -m scripts.chat_eval -i sft
```

> 两种模式的差异只在**数据规模**（CPU 用一小部分、GPU 用较多），数据**类型选择一致**，都走第 4 节的代码修改。

## 4. nanochat 使用中文数据集的代码修改思路

### 4.1 改动总览

| 文件 | 现状（英文） | 改成（中文） |
|------|------------|------------|
| `nanochat/dataset.py` | `BASE_URL` 指向 HF `karpathy/climbmix-400b-shuffle` | 指向中文语料仓库（ModelScope 或本地打包） |
| `scripts/tok_train.py` | 默认 vocab 32768 | 中文建议 65536（`--vocab-size` 已支持） |
| `tasks/common.py` | `load_hub_dataset()` 用 `huggingface_hub` 从 HF 下载 | 新增 `load_modelscope_dataset()` 从 ModelScope 下载，或保持 HF 格式只换 repo 名 |
| `tasks/smoltalk.py` | 加载 `HuggingFaceTB/smol-smoltalk` | 换成 `opencsg/smoltalk-chinese` |
| `tasks/mmlu.py` | 加载 `cais/mmlu`，英文 prompt | 换成 C-Eval / CMMLU，prompt 改中文 |
| `tasks/gsm8k.py` | 加载 `openai/gsm8k` | 换成 GSM8K_zh（`####` 与 `<< >>` 格式保留则 reward 可复用） |

### 4.2 具体修改思路（以最小改动为原则）

**① Tokenizer 重训（必做）**
```python
# scripts/tok_train.py 已支持 --vocab-size，无需改代码
python -m scripts.tok_train --max-chars=2000000000 --vocab-size=65536
```

**② 预训练数据源（dataset.py）**
```python
# 方案 A：直接换成 ModelScope 上的中文 parquet 仓库
BASE_URL = "https://modelscope.cn/datasets/modelscope/SkyPile-150B/resolve/master"  # 需确认文件布局
MAX_SHARD = ...  # 按中文语料分片数调整

# 方案 B（推荐，改动最小）：先本地把中文语料打包成与 ClimbMix 相同格式
# ① 抽样下载 Ultra-FineWeb-zh 的若干 part（单文件 URL，无需全部下载）：
#    https://modelscope.cn/datasets/OpenBMB/Ultra-FineWeb/resolve/master/data/ultrafineweb_zh/ultrafineweb-zh-part-{i:03d}-of-256.parquet
#    i 隔片取（如 0,4,8,...），256 片中任取子集即可，保证来源多样
# ② 列名不同：zh 分片是 content / score / source 三列 → 只取 content 并改名 text
#    （ClimbMix 是单列 "text"，dataset.py 的 rg.column('text') 依赖这一列）
# ③ 全局洗牌（seed=42）→ 按 ~250M 字符分桶 → 写单列 "text" 的 parquet
#    （复用 dev/repackage_data_reference.py 的思路完成 ②③）
# ④ BASE_URL 指向本地目录或任意可下载 URL，dataset.py 其余逻辑不动
#    于是 -n 8 / -n 170 等按片数选取的语义原样保留
```

**③ SFT 任务替换（tasks/）**
```python
# tasks/smoltalk.py：只需换 repo_id
self.ds = load_hub_dataset("opencsg/smoltalk-chinese", split=split)

# tasks/mmlu.py：新增 C-Eval 分支（或新写 tasks/ceval.py）
# 数据结构：question / A B C D / answer，与 MMLU 几乎一致，
# 只需把 render_mc 的英文 prompt 换成中文：
#   "Multiple Choice question: ..." → "以下是中国关于{科目}考试的单项选择题：...\n请选出正确答案。"
# 保留 A/B/C/D 四选一 + Loss Mask 逻辑不变

# tasks/gsm8k.py：换成 GSM8K_zh
# 若翻译版仍保留 "#### 数字" 与 "<<表达式=结果>>"，则：
#   GSM_RE 正则、extract_answer、reward 全部零改动
```

**④ RL 阶段（chat_rl.py）**
```python
# 只需替换 train_task / val_task 的数据源
train_task = GSM8K_zh(subset="main", split="train")  # 或复用 GSM8K 类换 repo_id
# 其余（num_samples=16、render_for_completion、reward）全部不动
```

### 4.3 已经核实的两处关键事实

1. **C-Eval 的 split 与标签**（已核实）：共 13,948 题 / 52 学科，每个学科分 **dev / val / test** 三部分：
   - `dev`：每科 5 题带解析（few-shot 用），共 260 题
   - `val`：标签公开，共 **1,346 题**，官方明确推荐"开发期用它做参考"
   - `test`：12,342 题，**答案不公开**（需官网提交评测）
   - → 训练/验证直接用 `dev + val`（1,606 题），不要碰 test。字段为 `question / A / B / C / D / answer`，与 MMLU 完全同构，`render_mc` 只需改 prompt 文字。
2. **GSM8K_zh 的格式**（已核实）：7,473 训练 + 1,319 测试（GPT-3.5 直译 GSM8K），但有两个坑：
   - 字段名是 **`question_zh` / `answer_zh`**，不是 `question` / `answer`，加载后必须 rename（`gsm8k.py:54-55` 读 `row['question']`/`row['answer']`），否则取不到值
   - **test split 只给 `question_zh`、没有答案**（答案不公开），不能直接当验证集
   - → 训练用 `train` split；验证/RL reward 用 **train split 划出一部分**（或改用 `gsm8k-platinum`，其含答案）。`answer_zh` 是否保留 `#### 数字` / `<<表达式=结果>>` 需下载后抽查，若被改写则适配 `gsm8k.py:58-75` 的解析逻辑。

### 4.4 最小可行验证路径（跑通即算成功）

```
1. 用 SkyPile/Ultra-FineWeb-zh **隔片抽样**约 2B 字符重训 tokenizer → tok_eval 看中文压缩率是否明显优于旧词表
2. 用 ~2B 字符中文语料跑 runcpu.sh 预训练（6 层小模型）
3. 用 smoltalk-chinese + C-Eval(dev) + GSM8K_zh 跑 chat_sft（1500 迭代）
4. chat_cli 输入中文问题，观察能否用中文回复
```
